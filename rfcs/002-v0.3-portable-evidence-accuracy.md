# RFC 002: Portable evidence accuracy and interpretable scoring

- Status: Draft
- Authors: Planet B2B Inc. maintainers
- Created: 2026-07-17
- Target benchmark version: 0.3.0

## Problem

ADRB v0.2 made repository assessment idempotent and separated repository, platform,
organization, and outcome evidence. Three real-world pilots exposed remaining accuracy and
interpretation problems:

1. harness conventions are recognized inconsistently: `.cursor/**` can establish tool discovery
   but is not searched for tool guidance, `.ai/skills/**` is not recognized, and mixed-case
   `Agents.md` is missed;
2. whole-file term co-location still produces false positives when an unrelated `stale` cache test
   or a distant `AGENTS.md` comment appears in a large script;
3. a global content-file cap lets a large `.ai/runs/**` or documentation corpus crowd authoritative
   root guidance out of the candidate set;
4. deterministic repository controls cannot accept source-backed semantic evidence when a project
   uses a legitimate, unrecognized convention;
5. the reported percentage uses 40 as its denominator even when a repository-only run cannot
   establish platform, organization, or outcome controls; and
6. security level 1 combines secret/data handling with vulnerability-response policy, causing a
   private repository with strong read-only data boundaries to pass no readiness profile.

The Open Mercato pilot scored 14/40 despite a mature harness. Its canonical `.ai` tool declaration
and merge-authority guidance were missed, while unrelated cache and development scripts produced
two higher-level passes. The Dialer pilot scored 7/40. Its lack of tests, CI, recovery, and run
records was real, but its Cursor-native planning and review workflow was under-read and the result
incorrectly implied that even approved read-only analysis was unsupported.

The Python/uv pilot scored 3/40 despite an exact Python constraint, `uv.lock`, a canonical quality
script, Python verification in CI, and two tracked system/implementation specifications. The low
readiness conclusion remained directionally correct because tooling, security, governance,
learning, observability, and recovery contracts were incomplete, but Python vocabulary and the
`docs/spec-*.md` layout caused six repository false negatives.

## Proposed normative change

ADRB v0.3:

1. adds generic `.ai` and common `Agents.md` path variants to portable controls, plus a declarative
   detector adapter for recognized Claude, Codex, Copilot, Cursor, Kiro, and OpenCode layouts,
   without changing v0.1 or v0.2;
2. adds an optional proximity window to `content_terms`, requiring qualifying terms to appear in a
   bounded local section rather than anywhere in a large file;
3. adds optional per-pattern candidate limits and honors catalog pattern order, keeping
   authoritative entry points visible without scanning unbounded corpora;
4. tightens agent-guidance and knowledge-curation enforcement controls with control-specific
   required terms;
5. permits commit-bound, expiring, source-backed `repository` claims for explicitly eligible
   controls when deterministic discovery is inconclusive; these remain labelled
   `agent-collected`, never `repository-detected`;
6. reports a repository-detected score and the maximum score the offline repository collector can
   establish, alongside the normative 40-point score;
7. splits security level 1 into agent secret/sensitive-data boundaries and a separate level-2
   security-reporting control; and
8. recognizes explicit agent review workflows as level-1 governance evidence while retaining
   ownership and merge authority as level 2.

The core scanner remains network-free and model-free. Semantic claims are produced by an authorized
agent outside the scanner and are validated for benchmark version, repository, commit, scope,
timestamps, expiry, and eligible control.

## Evidence and research

The proposal is grounded in three sanitized pilot assessments:

- Open Mercato: 17 repository controls detected, 9 unmet, 17 unknown. `.ai/agentic.config.json`,
  `.ai/skills/**`, `AGENTS.md` merge rules, and 143 run units were under-read. `CTX-003` passed on a
  distant `AGENTS.md` comment in a generic development script; `LRN-003` passed on a stale-cache
  unit test.
- Dialer: 7 repository controls detected, 19 unmet, 17 unknown. The project genuinely lacked tests,
  CI, contribution policy, correction memory, run records, and coding-agent recovery controls, but
  had a tracked Cursor plan-author/reviewer/post-implementation-review workflow and explicit
  secret/PII rules. The case-sensitive collector also ignored tracked `Agents.md`.
- Python/uv pilot: 4 repository controls detected, 23 unmet, 17 unknown. The project had exact Python and
  dependency constraints, substantial tracked specs, a canonical quality script, and Python
  verification in CI, but its vocabulary and `docs/spec-*.md` layout were not recognized.

All three pilots had zero agent-collected claims. Their filesystem-only reports presented 14/40,
7/40, and 3/40 without explaining that the v0.2 repository-only ceiling is 23/40.

The implemented v0.3 draft was then rerun against the same commits with tracked files unchanged. Open Mercato moved to
15/40 with repository-detected progress 15/23 and passed `planning`; its generic `.ai` tooling and
merge authority were recognized, while the stale-cache and distant-comment false positives were
removed. Its remaining PR blockers are the substantive preflight/autonomy, run-envelope definition,
and recovery/stop-condition controls. Dialer moved to 10/40 with repository-detected progress 10/23 and
also passed `planning`; its capitalized `Agents.md`, Cursor-native review workflow, security
guidance, and plan corpus now count, while the genuine testing, CI, ownership, learning,
observability, and containment gaps remain blockers for PR creation. The Python/uv pilot's v0.2 and initial
v0.3 repository-only runs both scored 3/40. A sanitized calibration fixture establishes environment
setup, durable specifications, and Python verification while deliberately leaving the exact
`pyproject.toml` runtime-pin check unresolved for a future structural collector. The calibrated
v0.3 fixture scores 7/40 and still passes no readiness profile, preserving the substantive autonomy
blockers.

Constellation's `multi-llm-pr-review-pipeline` and `codex-grounded-pr-review-harness` knowledge-base
pages reinforce the same distinction: harness capability depends on grounded workflow,
verification, and runtime policy, not documentation volume or model identity.

## Scoring and compatibility impact

v0.3 scores are not comparable with v0.2 scores. The ten dimensions, four maturity levels,
consecutive-level scoring, 40-point maximum, and non-compensating readiness floors remain.

Security level 1 changes meaning to secret and sensitive-data boundaries. New ADRB-SEC-006 at level
2 captures security reporting and response. Existing `local-implementation` and `pr-creation`
security floors remain level 2, so neither profile is relaxed. The change only prevents the
read-only and planning profiles from depending on a public-style vulnerability policy.

The repository-detected score is explanatory, not a second readiness decision. Readiness profiles
continue to use the normative score and may include repository-detected, agent-collected, or
human-attested controls according to each control's evidence policy.

## Security, privacy, and misuse impact

Repository semantic evidence creates a risk that an agent over-interprets prose. v0.3 mitigates
this by requiring explicit control eligibility, exact target and commit binding, short-lived claims,
privacy-safe tracked-path references, tracked files matching HEAD, separate confidence labels, and fail-closed conflicts. Deterministic
matches take precedence. Human attestations do not silently override repository controls.

The evidence request instructs agents to cite tracked file paths and line anchors, describe the
control-specific derivation, and return `unknown` when evidence is partial. Source excerpts,
credentials, raw prompts, and sensitive logs remain prohibited.

The repository-visible denominator must never be described as certification or as evidence that
external controls are unnecessary.

## Alternatives

- Add every observed path to every keyword collector: rejected because it recreates broad false
  positives and couples portable controls to documentation volume.
- Normalize the 40-point score to the repository-only ceiling: rejected because it would hide
  unresolved platform and outcome maturity. v0.3 displays both values instead.
- Let attestations override any failed repository check: rejected because declarations cannot turn
  mechanically absent evidence into verified repository evidence.
- Relax PR-creation security, testing, governance, or resilience floors: rejected. The pilots
  support better evidence discovery, not weaker autonomy requirements.
- Patch v0.2 in place: rejected because published benchmark meaning is immutable.

## Rollout and conformance fixtures

The v0.3 suite must prove that:

- v0.1 and v0.2 catalogs and evidence bundles retain their historical behavior;
- generic `.ai` and Cursor-native harness conventions are discovered where control-specific;
- mixed-case `Agents.md` is discoverable;
- generic stale-cache and development-script terms do not establish knowledge or guidance
  enforcement;
- repository semantic claims are accepted only for eligible controls, exact repository/commit
  targets, repository scope, and unexpired evidence;
- deterministic evidence remains labelled separately and takes precedence;
- reports expose normative score, repository-detected score, repository-only ceiling, and evidence
  resolution without normalizing away unknowns;
- the Open Mercato-shaped fixture avoids the confirmed false positive/negative pattern;
- the Dialer-shaped fixture passes planning but still fails local implementation and PR creation;
  and
- the Python/uv-shaped fixture recognizes conventional Python setup, specs, and verification without
  treating `pyproject.toml` presence alone as a pinned runtime declaration.
