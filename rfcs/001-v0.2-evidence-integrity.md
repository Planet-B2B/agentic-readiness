# RFC 001: Evidence integrity and agent-assisted collection

- Status: Draft
- Authors: Planet B2B Inc. maintainers
- Created: 2026-07-17
- Target benchmark version: 0.2.0

## Problem

The v0.1 filesystem collector can treat generated reports and untracked local configuration as
repository evidence. Its broad keyword checks can also combine unrelated terms across a large
documentation corpus. These behaviors make repeated assessments non-idempotent and can label weak
artifact-presence signals as verified controls.

Repository inspection also cannot establish platform settings, organizational enforcement, or
outcome trends. Treating those expected unknowns as repository remediation gaps obscures the actual
work required.

## Proposed normative change

ADRB v0.2:

1. assesses tracked Git paths by default and exposes workspace scanning as an explicit provisional
   mode;
2. excludes generated reports, attestation files, and imported evidence bundles from repository
   collectors;
3. requires non-empty path evidence and co-located multi-term content evidence;
4. returns only qualifying files as evidence references;
5. labels repository matches as `repository-detected`, not as proof of operational enforcement;
6. separates repository, platform, organization, and outcome evidence scopes;
7. accepts a version-bound, target-bound agent evidence bundle for non-repository controls; and
8. keeps agent-collected evidence distinct from human attestations and future conformant adapters.

The agent orchestrates evidence collection. The scorecard remains the deterministic scoring
authority. Agent-collected evidence may satisfy an eligible external control, but it is never
reported as independently verified.

## Evidence and research

Pilot feedback found a clean assessment whose OBS-001 and OBS-002 results changed after the tool's
own report was written under `.agentic/reports`. A local untracked `.mcp.json` also satisfied a
tool-declaration control, and broad content checks cited every searched file rather than only the
files containing qualifying evidence.

## Scoring and compatibility impact

Control outcomes, evidence semantics, confidence labels, and the report schema change. v0.2 reports
are not score-comparable with v0.1 reports. Dimension scoring remains consecutive-level, the maximum
score remains 40, readiness floors remain non-compensating, and no v0.1 file is modified.

Several level-3 controls are split so repository configuration and external enforcement are separate
observable outcomes. A dimension earns level 3 only when every applicable level-3 control is met.

## Security, privacy, and misuse impact

Default assessment remains offline and read-only. Agent evidence collection must be separately
authorized, read-only, least-privileged, privacy-safe, and unable to modify benchmark policy or tool
authority. Errors, stale claims, target mismatches, and unavailable evidence fail closed to unknown
or a validation error; they never become a passing claim.

## Alternatives

- Silently patch v0.1: rejected because published scoring meaning is immutable.
- Treat any agent statement as verified: rejected because narration is not evidence.
- Require vendor APIs in the core scanner: rejected to preserve offline operation and neutrality.
- Keep scanning the whole workspace by default: rejected because local-only artifacts are not
  durable repository controls.

## Rollout and conformance fixtures

The v0.2 suite must prove that generated reports do not change scores, untracked files do not pass
the default assessment, unrelated documentation terms do not combine across files, references name
only qualifying files, evidence bundles are target- and version-bound, and expired evidence is
ignored.
