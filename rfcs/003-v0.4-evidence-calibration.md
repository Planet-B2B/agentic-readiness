# RFC 003 — ADRB v0.4 semantic and structural evidence calibration

- Status: Accepted for v0.4; implementation pending merge
- Release state: Unreleased; acceptance requires human review and merge of PR #11
- Target benchmark version: 0.4.0
- Related issues: #5, #7, #8, #9, #10

## Problem

ADRB v0.3 made repository evidence safer and more precise, but pilot assessments exposed four
remaining measurement problems:

1. Failure-containment guidance can use clear stop and escalation language without the detector's
   literal phrases, while the report hides meaningful partial coverage.
2. A failed multi-check control reports `confidence: none` even when one repository check passed,
   which readers can misinterpret as no relevant evidence.
3. Governance Level 2 accepts only `CODEOWNERS` as an ownership assignment, excluding other explicit
   tracked ownership maps.
4. Security Level 3 combines automated secret scanning with untrusted-input safeguards, allowing
   weak keyword evidence and preventing platform-native scanning from establishing its own outcome.

The current v0.3 implementation follows its catalog as written. Correcting these semantics therefore
requires a new immutable benchmark version rather than a package-only patch.

## Decision

### Semantic component evidence

Add a vendor-neutral `content_groups` evidence primitive. A control defines named outcome components
and synonymous terms for each component. The collector evaluates the components inside a bounded
window, reports the strongest matched and missing groups, and passes only when the configured number
of groups is co-located. Partial references remain visible without becoming a pass.

`ADRB-RES-002` will require co-located evidence for mutation scope, resource or retry bounds, a stop
trigger, escalation, and recovery ownership. Natural language such as `stop and ask` may establish a
stop or escalation component, but a human merge gate alone does not establish containment.

### Partial-check reporting

For unresolved v0.4 controls, Markdown reports will distinguish control confidence from individual
repository checks. They will state how many checks passed and name each blocking check. Status and
scoring remain binary; partial evidence does not earn a maturity level.

### Ownership maps

Add an `ownership_map` evidence primitive that recognizes non-empty conventional ownership files and
structurally identifiable component/path-to-owner mappings. `ADRB-GOV-002` will require an
ownership map, explicit accountable-human approval authority, and explicit accountable-human merge
authority. Conventional owner lists
require an accountable handle or contact; mapping placeholders and generic prose containing `owner`
or `reviewer` are insufficient. Platform enforcement remains `ADRB-GOV-003`.

### Split security outcomes

Retain `ADRB-SEC-003` for automated secret-leakage safeguards and add `ADRB-SEC-007` for enforced
untrusted-input safeguards. Both are Level 3 and therefore both must pass to earn security Level 3.

Add a `ci_command` primitive that structurally inspects enabled, integration-triggered scanner
actions and shell invocations rather than arbitrary command-like text. Manual-only workflows,
disabled, non-integration or allow-failure steps, ineffective shell branches, and display commands
such as `echo gitleaks` do not establish enforcement. Portable controls state outcomes; scanner and
CI-provider aliases and discovery paths remain in versioned adapters.
`ADRB-SEC-003` may also accept target-bound, expiring platform evidence for host-native scanning.
`ADRB-SEC-007` requires reviewable evidence of boundaries plus mechanical enforcement or tests; one
security outcome never implies the other. Its repository, platform, and organization agent-evidence
scopes are intentional because enforcement may reside in tracked adversarial harness tests, platform
sandbox policy, or organization-wide controls. Source-backed claims must name the scope where
enforcement actually resides; repository prose alone is insufficient.

## Compatibility and scoring

- ADRB v0.1, v0.2, and v0.3 files and behavior remain unchanged and reproducible.
- The default CLI, templates, schemas, and report version move to v0.4.0.
- The ten dimensions, four maturity levels, 40-point maximum, and readiness floors do not change.
- Security gains one Level 3 control, increasing the catalog from 44 to 45 controls without changing
  the maximum score.
- Scores from v0.3 and v0.4 are not directly comparable because evidence semantics change.

## Privacy and safety

All new collectors remain local, read-only, network-free, symlink-safe, bounded by existing file and
corpus limits, and retain no source content. Platform evidence remains optional, separately labeled,
least-privileged, target-bound where applicable, and expiring.

## Acceptance criteria

- Synonym-only stop/escalation guidance is reported as partial evidence, not erased or automatically
  promoted to a pass.
- Full containment coverage can pass without requiring v0.3's literal idioms.
- Failed multi-check controls identify the blocking evidence check and partial check count.
- Explicit ownership maps and conventional owner-contact lists pass; placeholders, descriptive
  maintainer prose, punctuation-only targets, negated authority, and ownership without authority
  guidance do not.
- Enabled integration-triggered secret-scanning invocations pass; comments, display commands,
  version/help commands, identity-shaped action substrings, post-close triggers, disabled steps,
  missing-runner jobs, reusable-job references, allow-failure paths, partially supported conditions,
  exit-status-swallowing shell blocks, and manual-only workflows do not.
- Platform-native secret-scanning evidence cannot satisfy untrusted-input safeguards.
- Historical v0.1–v0.3 regression tests and the v0.4 conformance suite pass.
